# Integrar Admin Pagos Wireframe con los microservicios

Objective: dejar la pantalla `Admin Pagos Wireframe` funcionando contra la API real del gateway, sin ruta mock, conservando el diseño del frame `0:2537` y el patrón ya entregado para Admin Productos.
Branch: `main`, sin creación de rama. Decisión explícita del usuario en L2: trabajar en el árbol actual y NO hacer commits ni tocar los cambios ajenos ya presentes.
Delivery: `exception-ok`, sin PR y sin commits por decisión del usuario.
Checks: backend `./mvnw test` y `./mvnw verify`; frontend `npx vitest run`, `npm run lint`, `npx tsc --noEmit`, `npm run build`. En PowerShell 5.1 los comandos se separan con `;`, nunca con `&&`.

## Specs

S1 — Alcance (petición literal del usuario): "Admin Pagos Wireframe haceme la integracion de front y back de esta pantalla con las skills que hay en el proyecto". Aceptación: `/admin/pagos` obtiene datos, filtros, orden, paginación y estados del gateway real; no queda ninguna ruta de datos mock para esta pantalla. Se aplican las skills del registro del proyecto: `java-springboot`, `vercel-react-best-practices` y `vitest`. Se mantiene la preferencia histórica: "no quiero modos mocks, quiero la integracion real funcionando ya". Decisión de entrega (L2): "Sin commits".

S2 — Diseño como fuente: `docs/OpenPencil/LaTiendita.fig` (page `0:3`, frame `0:2537`, 1440 × 1113) y `odd/tasks/admin-pagos-wireframe-mock.md` S1–S12. Se conservan las medidas desktop (sidebar 240, contenido 1136, cuatro KPI de 266 × 115 con gap 24, filas de 64) y el comportamiento responsive actual. Copy literal del frame: `Pagos`, `Exportar CSV`, `Conciliar pagos`, `Cobrado (30 días)`, `Pendiente de acreditación`, `Rechazados`, `Tasa de aprobación`, `Rango: Últimos 30 días ↓`, `Movimientos`, `Todos los pagos procesados por Mercado Pago`, `Buscar por pago, pedido o cliente...`, `Ordenar: Más recientes ↓`, `Ver →`, `Mostrando 1–8 de 48 pagos`. Los valores numéricos del wireframe son del seed y pasan a ser dinámicos; las etiquetas y el formato se conservan.

S3 — Contrato HTTP (congelado para backend y frontend):
- `GET /api/payments/admin/summary?days=30` → `AdminPaymentSummaryResponse`, extendida de forma aditiva: se conservan `paymentsToClear` y `paymentsInReview` (los consume Admin Resumen) y se agregan `totalPayments`, `approvedCount`, `pendingCount`, `rejectedCount`, `approvedVolume`, `pendingVolume`, `rejectedVolume`, `approvalRate` (entero, porcentaje redondeado), `approvalAttempts` y `rangeDays`. Ningún campo existente se renombra ni se elimina.
- `GET /api/payments/admin?q=&status=&days=&page=&size=&sort=` → `Page<AdminPaymentResponse>`; cada item expone `id`, `orderNumber`, `customerId`, `provider`, `paymentMethodId`, `paymentType`, `paidAt` (ISO-8601), `amount` y `status` (`APPROVED` / `PENDING` / `REJECTED`). Backend aplica `CurrentUser.requireAdmin()`, filtro por texto sobre `orderNumber` y `customerId`, filtro por estado, rango de días sobre `paidAt`/`createdAt` y paginación Spring (0-based).
- `status` se expone en el DTO como enum del servicio; la UI muestra `Aprobado` / `Pendiente` / `Rechazado` con el `PaymentStatusBadge` existente.
- No se crea ningún endpoint para `Exportar CSV` ni `Conciliar pagos`: el frame S3 los define como presentacionales y no hay flujo dibujado. No se inventa un contrato para ellos.

S4 — Suposición documentada sobre identidad del cliente: `PaymentEntity` no persiste nombre ni email del cliente (sólo `customerId`, `orderNumber`, `paymentMethodId`, `paymentType`). El listado admin mostrará `customerId` como cliente y NO inventará un nombre. El campo `email` de `AdminPayment` pasa a ser opcional y la línea se omite cuando no hay dato. No se agrega una llamada a customer-service: eso sería infraestructura nueva no pedida.

S5 — Adaptador frontend: `features/admin/services/admin.service.ts` conserva la firma pública `getAdminPayments` y la reescribe como adaptador real con `adminAuthHeaders()` (cookie `lt_access_token` → `Authorization: Bearer`), conversión de página 1-based de la UI a 0-based de Spring (`Math.max(0, uiPage - 1)`), constantes de tamaño/orden y `Promise.all` de listado + summary. Se elimina la lectura de `GET /admin/payments` del mock. Se agrega `features/admin/helpers/admin-payments.mapper.ts` espejo de `admin-products.mapper.ts`. Todo pasa por `unwrapPage`.

S6 — UI: los controles hoy inertes pasan a operar contra S3: búsqueda por pago/pedido/cliente, pills `Todos`/`Aprobados`/`Pendientes`/`Rechazados`, orden `Más recientes ↓`, paginación y rango de 30 días. La pantalla sigue el patrón de `admin-products-table.tsx`: componente cliente con estado, refetch y error de carga; el server component `AdminPaymentsPage` hace la carga inicial. El header y los KPI toman sus cifras del summary real. `Exportar CSV` y `Conciliar pagos` siguen presentacionales por S3.

S7 — Tests (RED → GREEN → REFACTOR): backend agrega tests del listado admin con filtros/paginación, del summary extendido y de que las peticiones sin rol admin son rechazadas, más un test que pruebe que los endpoints existentes de pago del cliente siguen igual. Frontend agrega tests del adaptador real (Bearer, conversión 1-based → 0-based, `Page.content`, mapper) y de los controles de la pantalla. Todo test pasa por la interfaz pública y cubre efectos observables.

S8 — Documentación: `docs/microservicios/payment-service.md` refleja los dos endpoints admin y el DTO extendido, y corrige la sección que hoy lista el listado admin como faltante. No se toca `.fig`, `README.md` ni `docs/design-system/README.md` salvo evidencia de un cambio de contrato visual.

S9 — Verificación y riesgo: se ejecutan los checks del header. Riesgo alto por (3) contratos que otros consumen: se extiende un DTO existente y se agregan endpoints; y por la conversión de paginación, que ya produjo un blocker real en Admin Productos. Por eso el cambio recibe un verificador independiente además de sus propios tests. Se registra cada check, incluidos los fallidos o no disponibles. RDD está activo (`on`, decidido por global); sin commits no hay lifecycle de review por work-unit, pero se ejecuta `gentle-ai review assess` sobre el diff final.
