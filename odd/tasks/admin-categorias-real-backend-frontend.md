# Integrar Admin Categorías con backend real

Objective: dejar `/admin/categorias` 100 % funcional contra la API real del gateway (alta, edición, borrado protegido, búsqueda/orden y estado activo), sin rama mock, reutilizando el scaffolding existente y los frames aprobados en `docs/design-system` §3.2.
Branch: `main` (preferencia explícita previa del usuario; push/PR los decide él). Delivery: `exception-ok` (acordado en el historial), **sin commits en esta entrega**: el usuario eligió "No commitear esta vez" (L6) porque el worktree tiene cambios ajenos sin commitear que se solapan con estas superficies. Checks: backend `./mvnw test` y `./mvnw verify`; frontend `npx vitest run`, `npm run lint`, `npx tsc --noEmit`, `npm run build`.

## Specs

S1 — Alcance (peticiones literales del usuario): "Ahora Implementame el frontend y el backend a forma real de estas pantallas. usando las skills, buenas practicas, etc ..." y, como contexto de las pantallas alcanzadas: "Quiero que a la pantalla Admin Categorias Wireframe Termines de armar sus menus para Editar y Nueva, mas lo que se mostraria al queres borrar una categoria, hacelo en frames que esten debajo de esa pantalla que esten ordenados Respeta el docs\design-system". Aceptación: con el stack real levantado, `/admin/categorias` lista, busca, ordena, crea, edita y protege el borrado contra el gateway; no queda fallback mock en esta pantalla. Se mantiene la preferencia ya registrada en el proyecto: "no quiero modos mocks, quiero la integracion real funcionando ya".

S2 — Decisión del usuario sobre borrado (respuesta literal): "Bloquear con 409 (Recomendado)". Aceptación: `DELETE /api/categories/{categoryId}` devuelve 409 con `ProblemDetail` cuando `productCount > 0`; el backend no borra ni reasigna productos. El frontend traduce ese 409 a un mensaje observable en el diálogo de confirmación y no cierra el modal como si hubiera éxito. No se introduce un token de color `danger`: se conservan los grises del design system.

S3 — Contrato HTTP congelado para backend y frontend:
- `GET /api/categories?q=&featured=&page=&size=&sort=` → `Page<CategoryDto>` sin cambios de ruta ni de verbo. Cada item expone `categoryId` (string), `name`, `slug`, `description`, `featured` (flag del Home, existente), `active` (boolean nuevo, visible en tienda), `imageUrl` (string|null), `productCount` (existente) y `lowStockCount` (nuevo, derivado con el mismo umbral que `/api/products/admin/low-stock`).
- `POST /api/categories` → 201 + `Location`; `PUT /api/categories/{categoryId}` → 200; `DELETE /api/categories/{categoryId}` → 204 con la guarda 409 de S2. Se reutilizan las rutas existentes: el gateway ya exige `hasRole("admin")` para POST/PUT/DELETE en `/api/categories/**` y permite GET público. No se crea un prefijo `/admin` paralelo ni se cambia el gateway salvo evidencia de un hueco.
- Persistencia en `categories` con el mecanismo del repo (`ddl-auto=update`, sin Flyway): columnas nuevas `active`, `image_url` y `slug`. Supuesto documentado: `slug` se deriva de `name` al crear, se guarda y se conserva al editar si el formulario no envía otro valor; las filas existentes con `slug` nulo se serializan con el slug derivado y se materializan al editarlas. `active` por defecto `true` (nulo se interpreta como activo) para no alterar filas existentes. `featured` NO se reutiliza como `active`: pertenece al Home.
- Errores: se conserva el `ProblemDetail` existente de `GlobalExceptionHandler` (404 no encontrado, 409 duplicado/nombre en uso, 400 validación y orden inválido).

S4 — Adaptador frontend: `features/admin/services/admin.service.ts` conserva la firma pública `getAdminCategories`, elimina la rama mock `/admin/categories`, envía `adminAuthHeaders()` (cookie `lt_access_token` → `Authorization: Bearer`), reenvía `q`, `featured`, `sort` y paginación, aplica la conversión 1-based→0-based ya establecida para `Pageable`, y mapea `CategoryDto` → `AdminCategory` reutilizando `unwrapPage`. `types/categories.ts` incorpora `active`, `imageUrl` y `lowStockCount` sin cambiar el significado de `featured` ni de `productCount`.

S5 — Mutaciones: `features/admin/actions/category-actions.ts` (o el archivo de acciones que corresponda según el patrón real de `product-actions.ts`) expone crear, editar, eliminar y alternar `active`, reenvía el Bearer de la cookie en cada_mutación y ejecuta `revalidatePath("/admin/categorias")`. La acción de eliminar distingue 204 de 409 y devuelve un estado de error visible, sin revalidar como éxito. Se corrige el punto débil actual: la acción de categorías hoy no propaga autenticación.

S6 — UI: los controles hoy inertes pasan a operar contra S3: `+ Nueva categoría`, búsqueda por nombre, `Ordenar: A–Z`, selección de fila, panel de detalle con imagen, `Editar categoría`, `Eliminar categoría` y el checkbox `Categoría activa`. Los dos formularios y el diálogo de confirmación siguen la forma y los tokens de los frames `566369648:276`, `566369648:318` y `566369648:358` (cards 640 × 686 y 480 × 368, scrim al 45 %, Inter, grises, radios 8/12, espaciados 4–32). Se separa la UI de modal en componentes propios, como en Admin Productos. Se conservan las medidas desktop (sidebar 240, main 1200, contenido 1136) y el comportamiento responsive actual. El campo de imagen es una URL de imagen (supuesto documentado: no existe endpoint de upload para categorías ni en el diseño ni en `ImageStorageService`, que es product-only); el placeholder `[ Imagen ]` permanece mientras no haya URL.

S7 — Tests (RED → GREEN → REFACTOR): una prueba RED por regla pedida, por la interfaz pública y con efectos observables (respuesta, header, estado persistido). Backend: alta/edición con `active`, `imageUrl` y `slug` conservado; `lowStockCount` derivado; borrado 409 con productos y 204 sin ellos; búsqueda `q` y orden; y un test que pruebe que `GET /api/categories` sin filtros sigue igual. Frontend: adaptador real (Bearer, `Page.content`, conversión de página), acciones (auth propagada, revalidación y 409) y controles de la pantalla. Si un runner no está disponible, se registra la excepción con evidencia, nunca se inventa RED/GREEN.

S8 — Documentación: `docs/microservicios/product-service.md` refleja el contrato de S3 y la guarda de S2. `docs/design-system/README.md` §3.2 ya quedó actualizado en el turno de diseño y NO se incluye en los commits de este feature por contener cambios previos no separables.

S9 — Verificación y riesgo: riesgo alto por (1) datos y efectos irreversibles (columnas nuevas, guarda de borrado) y (3) contratos que otros consumen (DTO ampliado y nuevo parámetro `q`). Por eso, además de los checks propios, el change recibe un verificador independiente con baseline y probes derivados de S1–S8. RDD está `on` (global); se evalúa cada work-unit commit y se sigue el lifecycle nativo sólo si aplica. Se registran todos los checks, incluidos los fallidos o no disponibles.
