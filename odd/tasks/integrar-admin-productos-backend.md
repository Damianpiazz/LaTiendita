# Integrar Admin Productos Wireframe con los microservicios

Objective: dejar la pantalla `Admin Productos Wireframe` 100 % funcional contra la API real del
gateway, con las acciones del wireframe operativas y los componentes no definidos diseñados
según `docs/design-system`, dibujados en OpenPencil e implementados después en el frontend.
Branch: `main` (preferencia explícita previa del usuario; el push lo hace él).
Delivery: `exception-ok` — commits por unidad de trabajo, sin PR, sin ramas de feature.
Checks: backend `./mvnw test` y `./mvnw verify`; frontend `npx vitest run`, `npm run lint`,
`npx tsc --noEmit`, `npm run build`; diseño `openpencil analyze spacing/colors` y `openpencil lint`.

S3 — Contrato HTTP (congelado para backend y frontend):
- `GET /api/products/admin/summary?q=&categoryId=` → `AdminProductSummaryResponse { totalProducts, totalCategories, totalLowStock, lowStockThreshold }`.
- `GET /api/products/admin?q=&status=&categoryId=&page=&size=&sort=` → `Page<AdminProductResponse>`; cada item expone `productId` (string), `name`, `sku`, `category`, `price`, `stock`, `status` (`"publicado"|"borrador"|"agotado"`) y `published` (boolean). `status` se deriva en el backend: `agotado` si `quantity <= 0`, si no `publicado` cuando `published=true`, si no `borrador`.
- `POST /api/products/admin/status` con `{ productIds: number[], published: boolean }` → 204. `DELETE /api/products/admin` con `{ productIds: number[] }` → 204.
- `GET /api/products/admin/export.csv?q=&status=&categoryId=&sort=` → `text/csv` con el mismo filtrado que el listado.
- Alta y edición reutilizan los endpoints existentes `POST /api/products` y `PUT /api/products/{productId}`; no se crea un contrato paralelo.
- Persistencia: columna nueva `published` en `ProductEntity`, con valor por defecto `true` para filas existentes, usando el mecanismo de esquema del repo (`ddl-auto=update`). `featured` NO se reutiliza: pertenece al Home.

S4 — Adaptador frontend: `features/admin/services/admin.service.ts` conserva la firma pública `getAdminProducts` y agrega rama real con `adminAuthHeaders()` (cookie `lt_access_token` → `Authorization: Bearer`), parámetros de query para búsqueda/estado/categoría/orden/página y mapeo DTO → `AdminProduct` reutilizando `unwrapPage`. Se agrega el acceso a `/api/products/admin/summary` para el subtítulo `48 productos · 6 categorías · 5 con stock bajo`; los totales dejan de venir del seed. Para esta pantalla no se conserva ninguna rama mock: se elimina el fallback a `/admin/products` en `getAdminProducts`, porque L5 exige modo real sin mock.

S5 — Mutaciones: `features/admin/actions/product-actions.ts` con `"use server"` para crear, editar, publicar/archivar en lote, eliminar en lote y exportar CSV. Cada acción reenvía el Bearer de la cookie y ejecuta `revalidatePath("/admin/productos")`. El patrón se toma de `features/admin/actions/category-actions.ts`, corrigiendo el punto débil de esa acción: acá sí se propaga la autenticación. El gateway ya exige `hasRole("admin")` en `/api/products/admin/**` y en POST/PUT/DELETE de productos; no se cambia el gateway salvo evidencia de un hueco.

S6 — UI: los controles hoy inertes pasan a operar contra el contrato S3: búsqueda por nombre o SKU, pills `Todos`/`Publicados`/`Borradores`/`Sin stock`, selector de categoría, `Ordenar: Recientes ↓`, paginación, `Exportar CSV`, bulk bar `Publicar`/`Archivar`/`Eliminar`/`Limpiar`, `Editar` y `+ Nuevo producto`. Los modales y el diálogo de confirmación se implementan con la forma y los tokens de los frames creados en S2. El formulario administra `images: string[]` con controles para agregar y quitar referencias; en edición se cargan desde el detalle real del producto (`GET /api/products/{productId}`) y la primera imagen se usa como principal. El card del formulario respeta la altura del viewport: contenido scrolleable dentro del modal, sin desbordar el frame. Se conservan las medidas desktop del wireframe (sidebar 240, main 1200, contenido 1136, filas 64) y el comportamiento responsive actual.

S7 — Tests (RED → GREEN → REFACTOR): backend agrega tests de la derivación de `status`, del listado admin con filtros/paginación, del summary, de publicar/archivar/eliminar en lote y del CSV, más un test que pruebe que `GET /api/products` sin filtros sigue igual. Frontend agrega tests del adaptador real (incluido el header Bearer y el `Page.content`), de las actions (auth propagada y `revalidatePath`) y de los controles de la pantalla. Todo test pasa por la interfaz pública y cubre efectos observables (respuesta, headers, estado persistido).

S8 — Documentación: `docs/microservicios/product-service.md` refleja los endpoints admin, el campo `published` y la derivación de `status`; `docs/design-system/README.md` registra los tres componentes nuevos y sus frames; `README.md`/`frontend/README.md` sólo se tocan si el contrato o el puerto cambia.

S9 — Verificación y riesgo: se ejecutan los checks listados en el header. Riesgo alto por (1) datos y efectos irreversibles: columna nueva y borrado masivo, y (3) contratos que otros consumen: nuevos endpoints y DTOs. Por eso el cambio recibe un verificador independiente además de sus propios tests. Se registra el resultado de cada check, incluidos los fallidos o no disponibles.
